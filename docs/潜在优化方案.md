# 潜在优化方案

按证据优先，不改变“有效图片逐张传输、顺序观看、原图只读”的目标。

1. 完成真实源接口验证：确认GStreamer写入方式、目录交接和任务开始/结束约定；稳定窗口不是强完成信号。若生产端可发完成通知，可增加独立适配器，不修改通用队列协议。
2. 先观察地面持久写入：实测保存均值约17.2ms，其中持久写入约13.3ms。可比较存储位置/设备，但不能直接移除Flush或提前ACK；成功样本也不代表故障尾延迟。
3. 编码准备与网络等待重叠：若真实CPU计时证明编码明显，可考虑有界预处理工作者。需保持数字序号、缓存预算、失败重试和SQLite单写所有权，先做回归再启用。
4. 网络弱信号与遥测共存：记录重连、应用吞吐、积压并同步测量MAVLink质量，再确定限速；应用重连不能直接推算无线丢包率。自适应码率需明确定义恢复与质量下限。
5. 长期状态/地面历史规模：测量SQLite、目录扫描和磁盘增长，确认任务保留策略，禁止自动删除待传/未显示数据。日志轮转不代表总体空间受控。
6. ACK流水线只有在逐图等待确为主要瓶颈后讨论。它会增加重传窗口、去重和崩溃恢复复杂度，不是当前封装的顺带修改。

已完成的循环优化：成功ACK后不再固定睡眠、就绪缓存按需补充；历史200张256KiB/s从19.273秒到15.744秒，现场负载不完全一致，不作统计显著性结论。此次封装复用该实现，不重新调默认限速。

MP交互优化由另一个对话负责，主仓库不并行修改它。Ubuntu22.04、真实插件、磁盘不足、物理断链、长期运行和MP宿主恢复仍是验收优先项。
